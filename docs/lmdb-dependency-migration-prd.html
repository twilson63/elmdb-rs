Migrate elmdb-rs from lmdb 0.8 to heed 0.22

Definition: In this project, the "LMDB dependency" is the Rust crate that native/elmdb_nif/src/lib.rs uses for every storage operation: environment lifecycle (builder, flags, sync), the single unnamed database handle cached in DbState / hot_handles, read/write transactions (used by get, the empty-key put path, the background flush worker), cursor scans (list, iterator_next, match_pattern), and the lmdb::Error → Erlang atom table. A successful migration replaces this crate while keeping the Erlang-visible API (src/elmdb.erl) and error-atom semantics byte-for-byte identical.

Non-goals: No engine change (MDBX/sled/redb are out — different on-disk formats). No behavioral changes to the overlay/flush design, no new API functions (e.g. delete), no fix for the pre-existing put/3 key-size validation gap (tracked separately), no changes to src/elmdb.erl or the test suite semantics.

Why (evidence)

  • lmdb 0.8.0: last release 2016; RustSec advisory RUSTSEC-2022-0001 declares it unmaintained; vendors a ~2014 LMDB and bitflags 1.x.
  • lmdb-rkv 0.14.0 (the advisory's suggestion): Mozilla archived it; sys crate stale 4+ years.
  • heed 0.22.1 (Meilisearch): actively maintained, production-proven, tracks LMDB mdb.master, keeps the LMDB 0.9 on-disk format so existing databases stay readable.

Constraints

  • On-disk compatibility: databases written by the old crate must open unchanged (both are LMDB 0.9 format).
  • Error atoms returned to Erlang must not change (tests assert on them; downstream code matches on them).
  • Threading model unchanged: read txns on scheduler/dirty threads, write txns on the flush worker and NIF threads; txns never cross threads.
  • heed 0.20+ enforces one open Env per canonical path (EnvAlreadyOpened). Our global ENVIRONMENTS registry already guarantees this, but the close/reopen path in LmdbEnv::ensure_open must fully drop the old Env (strong_count check) before rebuilding.
  • Never clone the inner heed::Env; only clone the wrapping Arc<Env> so the existing strong-count close logic keeps working.
